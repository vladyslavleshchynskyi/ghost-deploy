❯ "Develop one click script to deploy ghost blog platform at a cloud provider   
  (AWS, GCP, Azure, Hetzner, etc) with no public SSH access, only through       
  tunnels (any provider/app)" в мене авс адмін-доступ через SSM Session         
  Manager, блог публікуватиму через Tailscale Funnel. Вже створив               
  IAM-користувача з AdministratorAccess, aws configure (eu-north-1), встановив  
  aws cli, jq і session manager plugin. У Tailscale увімкнув MagicDNS і         
  HTTPS-сертифікати, дозволив funnel у політиці, згенерував одноразовий auth    
  key, поки нічого не пиши а проаналізуй

● Подивився оточення: aws 2.41.2, jq 1.8.2 і session-manager-plugin встановлені,
  регіон eu-north-1, sts повертає user/deployer. Папка testtask порожня, якщо
  не рахувати rbac-test-task; вважаю, що вона стосується іншого завдання.

  Як я бачу архітектуру

  [Ваш ПК] --aws cli--> CloudFormation / EC2 API
       \--SSM Session Manager (вихідний 443 з інстансу)--> адмін-доступ до EC2

  [Інтернет] --> https://ghost.<tailnet>.ts.net (Tailscale Funnel, 443)
                      --> tailscaled на EC2 --> 127.0.0.1:2368 (Ghost) --> MySQL
  8

  - EC2 з Ubuntu 24.04 або AL2023, t3.small (2 ГБ) плюс swap. Менше не
    вистачить, бо Ghost і MySQL разом займають ~1.2–1.5 ГБ. AMI беремо з
    публічного SSM-параметра, без хардкоду.
  - Security Group без жодного inbound-правила. Key pair не створюємо, sshd
    вимикаємо. Так вимога «no public SSH» виконується з запасом: на інстанс
    узагалі нічого не відкрито.
  - IAM instance profile з AmazonSSMManagedInstanceCore і правом читати та
    видаляти один SSM-параметр.
  - Ghost у Docker Compose: офіційний образ ghost і mysql:8. Ghost слухає лише
    127.0.0.1:2368, назовні його виводить тільки Funnel.
  - Інфраструктуру описати в CloudFormation, а запускати bash-обгорткою. Так
    отримуємо ідемпотентність, чистий destroy одною командою і зрозумілий
    результат для рев'юера.

  Неочевидні ризики

  1. Перехоплення адмінки (критично). Коли Funnel уже працює, а власника ще не
     створено, перший відвідувач /ghost/#/setup стає власником блогу. Тому
     скрипт має сам створити owner-акаунт через Admin API
     (/ghost/api/admin/authentication/setup/) зі згенерованим паролем, і лише
     після цього вмикати Funnel.
  2. Auth key не можна класти в user-data. User-data видно через
     describe-instance-attribute і IMDS. Краще так: обгортка кладе ключ у SSM
     Parameter Store (SecureString), інстанс читає його через свою IAM-роль і
     одразу видаляє параметр.
  3. Одноразовий ключ заважає повторним запускам. Якщо деплой впаде після
     tailscale up, повторний запуск з тим самим ключем не спрацює. Можна взяти
     reusable-ключ із тегом (наприклад, tag:ghost) і коротким терміном дії, або
     лишити одноразовий і в README писати «на кожен деплой новий ключ».
  4. Node key expiry. Без змін блог «зникне» приблизно через 180 днів. Пристрої
     з тегом мають вимкнений expiry за замовчуванням, і це ще один аргумент на
     користь тега. Тоді в ACL nodeAttrs funnel має покривати саме цей тег, а не
     лише вашого користувача.
  5. Ghost url має збігатися з https://<host>.<tailnet>.ts.net. Назву tailnet
     заздалегідь не знаємо. Тому на інстансі порядок такий: tailscale up →
     tailscale status --json | jq .Self.DNSName → запуск Ghost з цим url → setup
     → tailscale funnel --bg 2368.
  6. Redirect loop за проксі. Ghost з https-url зациклюється на редиректах, якщо
     не отримує X-Forwarded-Proto: https. Треба на практиці перевірити, які
     заголовки ставить tailscale serve/funnel. Якщо цього заголовка немає,
     додамо між ними легкий Caddy.
  7. Мережа. SSM-агенту і Tailscale потрібен вихід в інтернет. Найдешевше дати
     публічний IPv4 при повністю закритому inbound. Приватна підмережа з VPC
     endpoints і NAT коштувала б $30+ на місяць, для тестового завдання це
     зайве. У README варто пояснити, що публічний IP використовується тільки для
     вихідного трафіку.
  8. Windows і Git Bash.
     - MSYS перетворює аргументи на кшталт /ghost/ts-authkey на шлях C:/Program 
       Files/Git/.... Потрібен MSYS_NO_PATHCONV=1.
     - aws у text-режимі на Windows віддає \r, тож вивід треба чистити tr -d 
       '\r'.
     - User-data не повинен потрапити на інстанс із CRLF.
  9. Перевірка «готово». Інстанс записує фінальний URL у SSM-параметр. Обгортка
     чекає на нього, робить curl до Funnel-URL і чекає 200. Перша видача
     сертифіката і DNS-пропагація для Funnel можуть тривати кілька хвилин.
  10. SMTP. Без пошти не працюють запрошення і magic links, сам блог і адмінка
      працюють. Пропоную лишити SMTP опційним через змінні середовища.

  Що буде в репозиторії

  - deploy.sh: перевіряє залежності, кладе ключ у SSM, створює стек, чекає
    готовності, виводить URL і креди адміна.

  2. Ghost 6 (поточна major-версія) у простому compose (Ghost + MySQL)
     підходить? Офіційний ghost-docker стек з ActivityPub і Tinybird тут, на мою
     думку, зайвий.
  3. CloudFormation плюс bash-обгортка чи вимагається суто aws cli без CFN?
  4. SMTP потрібен зараз чи лишаємо опційним?
